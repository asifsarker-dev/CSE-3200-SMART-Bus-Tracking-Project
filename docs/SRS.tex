\section{Introduction}

\subsection{Purpose}
This Software Requirements Specification (SRS) document details the complete functional and non-functional requirements for the \textbf{Smart Public Bus E-Ticketing \& Passenger Counting System}. It establishes the baseline for mobile application development (React Native / Expo), backend API construction (Node.js / Express / MongoDB), sensor count simulation, and verification matrices for the CSE 3200 academic project.

\subsection{Document Conventions}

    \item \textbf{US-xx}: User Story identifier.

\subsection{Project Scope}
The system modernizes local public bus operations by eliminating manual paper tickets and unrecorded cash transactions. It consists of:
\begin{enumerate}[noitemsep]
    \item A mobile application for bus conductors facilitating rapid distance-based fare calculation, single-tap ticket issuance, and offline transaction caching.
    \item A passenger interface for on-screen digital tickets, QR verification, and real-time crowd level visibility.
    \item An automated passenger counting simulation engine modeling bus door sensor crossings without physical hardware costs.
    \item An administrative analytics engine providing operators with revenue reconciliation and leakage audit trails.
\end{enumerate}

\section{Overall Description}

\subsection{Product Perspective}
Traditional local public transit relies on manual cash handling and paper ticket rolls. Field surveys reveal that conductors face high stress counting loose change on crowded, moving buses, leading to frequent passenger disputes and revenue leakage of 15--25\%. Existing solutions such as \textit{bdtickets}, \textit{Shohoz}, and \textit{Akota} are built exclusively for intercity coach travel with advance seat bookings, leaving intra-city transit completely unaddressed.

\subsection{User Classes and Characteristics}
\begin{itemize}
    \item \textbf{Bus Conductor (Primary Operator):} Needs an ergonomic, high-contrast mobile interface with fast tap sequences ($< 1.5$ seconds) and resilient offline caching in poor signal environments.
    \item \textbf{Daily Commuter (End User):} Requires instantaneous digital ticket receipts with scannable QR proof and route crowd density insight.
    \item \textbf{Fleet Owner / Authority (Admin):} Needs auditable reports comparing ticket sales against sensor counts to detect cash skimming and optimize fleet schedules.
\end{itemize}

\subsection{Operating Environment}
\begin{itemize}[noitemsep]
    \item \textbf{Mobile Client:} Android 8.0+ and iOS 14.0+ via React Native / Expo SDK 51+.
    \item \textbf{Backend Server:} Node.js (v18.x / v20.x LTS) with Express REST framework.
    \item \textbf{Database:} MongoDB (v6.0+) for document-oriented trip and ticket storage.
\end{itemize}

\subsection{Design and Implementation Constraints}
\begin{itemize}[noitemsep]
    \item \textbf{Software Only Requirement:} The primary academic deliverable must be a software application; hosted static websites are strictly rejected per course rules.
    \item \textbf{Hardware Sensor Abstraction:} Physical infrared/optical counters are emulated through a realistic simulation engine and REST test harness.
\end{itemize}

\subsection{Non-Functional Requirements (NFR)}
\begin{itemize}
    \item \textbf{NFR-01 (Performance):} Mobile ticket generation must complete in $\le 1.5$s online, and $\le 200$ms in offline cache mode. REST API occupancy queries must resolve in $< 500$ms ($p95$).
    \item \textbf{NFR-02 (Fault Tolerance):} Device must withstand connection drops with zero ticket loss. Sync reconciliation must be fully idempotent.
    \item \textbf{NFR-03 (Security):} HTTPS transport, JWT session authorization, bcrypt password hashing, and HMAC-SHA256 digital ticket verification.
    \item \textbf{NFR-04 (Ergonomics \& Usability):} Touch targets $\ge 48 \times 48\text{ px}$, high-contrast UI (WCAG 2.1 AA $\ge 4.5:1$), and single-hand thumb navigation.
    \item \textbf{NFR-05 (Maintainability):} Clean modular structure with 100\% requirement-to-test traceability.
    \item \textbf{NFR-06 (Portability):} Cross-platform Android and iOS execution via Expo without native modifications.
\end{itemize}

\section{System Use Cases}

\subsection{Use Case UC-02: Rapid E-Ticket Issuance}
\begin{itemize}[noitemsep]
    \item \textbf{Primary Actor:} Bus Conductor.
    \item \textbf{Precondition:} Conductor authenticated with active shift bound to Bus ID.
    \item \textbf{Main Flow:}
    \begin{enumerate}[noitemsep]
        \item Conductor taps destination stop on mobile route layout.
        \item System computes fare via distance matrix (FR-02).
        \item Conductor taps ``Confirm \& Issue''.
        \item System generates signed Ticket UUID and displays digital QR receipt (FR-03).
        \item Shift revenue and passenger counter update automatically.
    \end{enumerate}
    \item \textbf{Alternative Flow (Offline):} If network is unavailable, ticket is assigned an offline deterministic UUID, saved to local storage (FR-05), and flagged with a ``Pending Sync'' badge without stalling the user.
\end{itemize}

\subsection{Use Case UC-07: Passenger Count Ingestion \& Occupancy}
\begin{itemize}[noitemsep]
    \item \textbf{Primary Actor:} Simulated Sensor Engine.
    \item \textbf{Main Flow:} Sensor generates boarding/alighting event $\rightarrow$ API updates live passenger register $\rightarrow$ Occupancy rate recomputed $\rightarrow$ Commuter live route display reflects updated crowding density.
\end{itemize}
